# 기술 설계

요구사항을 **어떤 구조와 처리 방식으로 구현하는지**를 설명하는 문서를 둔다. UI 디자인(색·타이포·컴포넌트)은 여기가 아니다.
ADR이 "왜 이 기술을 골랐나"를 결정 1건당 1개로 보존한다면, 여기 문서는 "그 결정 위에서 실제로 어떻게 돌아가나"를 적고
구현이 바뀌면 현행에 맞춰 갱신한다.

## 무엇을 두나

여러 스토리에 걸쳐 살아남는 설계만 둔다. 스토리 하나의 설계 결정은 harness 플랜(`plans/<KEY>.md` 2장)이 맡으므로
여기에 중복해서 쓰지 않는다.

| 문서 | 내용 | 소유 | 상태 |
|---|---|---|---|
| [논리 ERD](./erd.md) | 도메인별 엔티티·관계, 도메인 간 참조 규칙 | D 정리, 각 도메인 소유자가 자기 절 | 초안 |
| [물리 스키마 규칙과 마이그레이션 정책](./schema-rules.md) | 명명·타입·제약·공통 컬럼, 마이그레이션 도구와 파일 규칙, 변경 절차 | D | 초안 |
| [도메인 이벤트 목록](../renewal/events.md) | 누가 무엇을 발행하고 듣는지 | D(인프라), 각 발행 도메인 | 유지 중 |
| 워치 ↔ 폰 Data Layer 동기화 | 경로·형식, 루틴 내려받기·세션 올리기, 세션 소유권, 재연결 | B | 2주차 스파이크 전에 작성 |
| 인증 | 토큰 종류·수명·저장 위치·전달 방식, 401·403 응답, 공개 경로 | D·C | 인증 방식 결정 시 작성 |

이벤트 목록은 `harness.json`과 `backend/AGENTS.md` 트리거가 경로를 직접 가리키므로 `docs/renewal/`에 그대로 둔다.
옮기려면 두 파일을 같은 MR에서 고친다.

## 규칙

- ERD·스키마 규칙 변경은 계약 변경이다. backend 영역 엄격 판정(트리거 1)이고 D 승인이 필요하다.
- 구현 MR이 설계와 다르게 가야 하면 임의로 진행하지 않고 합의한 뒤 문서를 먼저 고친다(루트 `AGENTS.md` 1장).
- 값·임계치는 설정값 이름만 적는다. 제품 정책은 [요구사항 명세](../requirements/README.md)에 둔다.
- 문서를 추가하면 위 표에 넣는다.
