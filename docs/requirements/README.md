# 요구사항 명세

이 폴더에는 사용자가 제품을 사용하는 상황마다 제품이 어떻게 동작해야 하는지를 적는다.
사용자가 화면에서 보거나 직접 해 볼 수 있는 결과만 적고, 그 결과를 어떤 기술로 만드는지는 적지 않는다.

## 다른 문서와의 관계

| 질문 | 답하는 문서 |
| --- | --- |
| 왜 만드는가, 누구의 어떤 문제를 푸는가 | [기획서](../renewal/plan.md) |
| 사용자에게 무엇이 보장되어야 하는가 | 이 폴더 |
| 어떤 기술과 구조로 만드는가 | [ADR](../adr/README.md), [기술 설계 문서](../design/README.md), 업무 항목별 플랜 |
| 어떤 요청과 응답을 주고받는가 | `contracts/openapi.json` |

요구사항은 기술 문서보다 상위 문서다. 기술 문서는 요구사항을 만족시키는 방법을 정하고,
요구사항은 기술 문서의 내용을 가져오지 않는다.

## 항목 작성 규칙

### 요구사항

- 주어는 그 동작을 실제로 겪는 사람이나 제품이다. "회원은 사진으로 식사를 기록할 수 있다", "관리자는 수정 데이터를 검수할 수 있다", "제품은 기록을 보관한다"처럼 쓴다.
- 한 항목에는 사용자에게 의미가 있는 결과를 하나만 적는다.

### 인수 조건

인수 조건은 요구사항이 충족되었다고 인정하기 위해 확인해야 하는 결과다. 다음 세 가지가 드러나게 쓴다.

- 상황: 어떤 상태에서 시작하는가
- 행동: 사용자가 무엇을 하는가
- 기대 결과: 사용자가 무엇을 보거나 겪는가

기대 결과는 사람이 제품을 직접 조작해서 확인할 수 있어야 한다. 실패하는 경우도 사용자가 겪는 결과로 적는다.
예를 들어 "400 오류를 돌려준다" 대신 "저장되지 않고, 어떤 값이 잘못되었는지 안내한다"라고 쓴다.

### 쓰지 않는 내용

| 쓰지 않는 내용 | 잘못 쓴 예 | 바르게 쓴 예 |
| --- | --- | --- |
| 저장 방식, 테이블과 컬럼 이름 | 예측을 `meal_prediction`에 저장한다 | 모델이 예측한 결과가 사용자가 고친 값과 함께 남는다 |
| 라이브러리와 플랫폼 API | WorkManager가 업로드를 재시도한다 | 네트워크가 다시 연결되면 기록이 자동으로 서버에 올라간다 |
| 서버 내부 호출과 이벤트 | `MemberOnboarded`를 받으면 Program을 만든다 | 온보딩을 마치면 홈에서 목표 칼로리를 볼 수 있다 |
| HTTP 상태 코드, 오류 코드, API 경로 | 409 `MEMBER_ALREADY_ONBOARDED` | 온보딩을 이미 마친 회원에게는 온보딩 화면이 다시 나오지 않는다 |
| 코드 구조와 검사 규칙 | `:core` 순수 함수로 계산한다 | (기술 문서에 적는다) |
| 화면 배치와 디자인 | 촬영 버튼은 화면 하단 중앙에 있다 | 홈에서 한 번 눌러 촬영을 시작할 수 있다 |

카카오 로그인이나 Health Connect처럼 사용자가 직접 보고 권한을 허용하는 외부 서비스의 이름은 쓸 수 있다.

### 수치

- 팀이 합의한 수치만 쓴다. 기획서의 수용 기준(예: 앱 실행부터 운동 시작까지 3탭 이하)이 여기에 해당한다.
- 합의하지 않은 수치는 쓰지 않고 "추후 논의해야 하는 사항"에 올린다. 본문에서는 "Q-MEAL-03에서 정한 시간 안에"처럼 그 항목의 ID를 가리킨다.

## 추후 논의해야 하는 사항

각 파일의 마지막 절에 아직 정하지 않은 사항을 모은다.

| 열 | 내용 |
| --- | --- |
| ID | `Q-<도메인>-<두 자리>`. 번호는 재사용하지 않는다 |
| 논의할 사항 | 답이 하나로 정해지도록 구체적인 질문으로 쓴다. 이전 초안에 적혀 있던 값이 있으면 "이전 초안에서는 20으로 적었다"처럼 함께 적는다 |
| 관련 요구사항 | 이 사항이 정해지면 달라지는 요구사항 ID |
| 결정할 사람 · 기한 | |
| 결정 | 결정되면 결정한 내용과 날짜를 적는다 |

이전 초안에 적혀 있던 값은 결정된 값이 아니다. AI는 결정 칸이 비어 있는 사항의 값을 구현에 사용하지 않는다.
결정이 나면 관련 요구사항 본문에 반영하고, 그 행은 지우지 않고 결정 칸만 채운다.

## ID와 상태

- 요구사항 ID는 `REQ-<도메인>-<두 자리>`이며 번호는 재사용하지 않는다. 공통 요구사항은 `REQ-NF-`, 홈 화면은 `REQ-HOME-`을 쓴다.
- 표의 열은 ID, 요구사항, 인수 조건, MVP, 상태다.
- 상태는 `제안` → `확정` → `구현` → `폐기` 순서로 바뀐다. 폐기한 항목은 지우지 않고 상태만 바꾼다.

## 갱신

- 사용자에게 보이는 동작을 바꿔야 하면 먼저 팀과 합의하고 이 문서를 고친 뒤에 구현한다.
- 구현하면서 정한 기술적인 결정은 이 폴더가 아니라 플랜이나 기술 설계 문서에 적는다.
- 플랜의 "1. 기준 문서"에는 읽은 요구사항을 `REQ-MEAL-04`처럼 ID로 인용한다.
  플랜의 인수 테스트는 이 문서의 인수 조건을 기술 수준의 테스트로 구체화한 것이다.
- 다른 도메인에 영향을 주는 항목은 그 도메인 담당자를 MR 리뷰어로 지정한다.
- 문서를 추가하면 위 표에 넣는다.
