# 요구사항 명세 재작성 인계 문서

다른 컴퓨터에서 이 작업을 이어받는 세션을 위한 문서다. 이 파일은 작업용이므로 PR을 병합하기 전에 삭제한다.

## 1. 작업 목적

요구사항 명세에 테이블과 컬럼 이름, 라이브러리, 오류 코드, 팀이 합의하지 않은 수치가 섞여 있었다.
구현 전인데도 이 내용이 확정된 계약처럼 읽혀서, AI가 초안값을 그대로 구현할 위험이 있었다.
그래서 요구사항 명세 7개 파일을 사용자 수준으로 다시 쓰고, 기술 내용은 요구사항보다 낮은 등급의 문서가 맡도록 나눈다.

## 2. 현재 상태

| 항목 | 값 |
| --- | --- |
| 브랜치 | `docs/requirements-user-level` (최신 `main`에서 생성) |
| PR | https://github.com/TeamYumYum/kkugi/pull/9 |
| Jira | 없음. 사용자가 키 없이 진행하라고 지시했다 |
| 판정 | lite (문서만 변경) |
| 끝낸 파일 | `docs/requirements/README.md`(작성 규칙), `docs/requirements/common.md` |
| 남은 파일 | `member.md` → `meal.md` → `workout.md` → `coaching.md` → `growth.md` → `admin-ml.md` 순서로 작성 |

## 3. 진행 방식

- 작성 규칙은 `docs/requirements/README.md`에 있다. 파일을 쓰기 전에 반드시 읽고, `common.md`를 작성 예시로 참고한다.
- 파일을 하나 작성할 때마다 사용자에게 바뀐 점을 보고하고 확인을 받은 뒤에 다음 파일로 넘어간다. 여러 파일을 한꺼번에 쓰지 않는다.
- 보고할 때는 다음을 구분해서 알린다.
  - 사용자 수준으로 다시 쓴 항목과 그 전후 비교
  - 요구사항에서 뺀 기술 내용과, 그 내용을 어느 문서가 다뤄야 하는지
  - 이전 초안에 없었는데 새로 추가한 항목이나 질문
- 커밋과 PR 갱신은 사용자가 요청할 때만 한다. PR 본문의 "검토가 필요한 결정"과 "후속 작업"에 새로 생긴 내용을 덧붙인다.

## 4. README에 적히지 않은 결정

- 사용자 수준으로 바꿔 쓸 수 없는 개발 규칙 항목은 삭제하지 않는다. `common.md`의 "1.1 삭제를 논의 중인 항목"처럼 별도 절로 옮기고 내용은 고치지 않으며, 삭제 여부는 PR에서 논의한다.
- 요구사항에서 뺀 기술 내용은 따로 옮겨 적지 않는다. 원래 내용은 git 이력(커밋 `2010c0f`)에서 확인할 수 있다.
- 미결 목록 중 코드 구조에 관한 항목(예: 홈 화면을 둘 Android feature 모듈)은 요구사항에서 빼고 PR 본문에 적는다.
- 용어집, ERD, 이벤트 목록, API 규약, 스키마 규칙은 지금 고치지 않는다. 요구사항 7개 파일을 모두 작성한 뒤에 함께 점검한다.
- 각 파일의 머리말 표에서 담당자 칸은 지우고, "대상 사용자" 칸에 누구의 요구사항인지 적는다. 결정할 사람은 기존 문서의 A~F 표기를 그대로 쓴다.

## 5. 작성할 때 주의할 점

- 사용자는 요구사항 명세 작성을 매우 중요한 작업으로 보고 한국어 품질에 특히 신경 쓴다. 문장 성분과 조사를 생략하지 않고, 대상과 방법이 드러나게 완결된 문장으로 쓴다.
- 기획서에 없는 용어, 사용자 유형, 정책을 새로 만들지 않는다. 이전 세션에서 "모델 운영자"라는 사용자 유형을 지어냈다가 삭제했다. 새 용어나 정책이 필요해 보이면 질문으로 올리고 사용자에게 알린다.
- 사용자 유형처럼 열린 집합을 목록으로 고정하지 않는다. 목록이 있으면 AI가 그 목록을 전체로 받아들인다.
- 이전 초안의 `(가정)` 값은 본문에서 빼고 "추후 논의해야 하는 사항"의 질문 문장 안에 "이전 초안에서는 ~로 적었다"처럼 남긴다.
- 기획서 2장의 수용 기준(탭 수 등)처럼 팀이 합의한 수치는 본문에 그대로 쓴다.
- GitHub에서 물결표 두 개가 한 줄에 있으면 취소선으로 표시되므로, 문서와 PR 본문에서 물결표를 피한다.
