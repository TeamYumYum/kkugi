## 1. 범위

- 포함: 루틴 생성(AI 추천·직접)·수정, 다음 운동일 루틴의 워치 사전 전달, 워치·폰 Workout Mode(세트 기록·휴식 타이머·심박 요약), 세션 소유권, 워치 → 폰 → 서버 세션 전달과 오프라인 업로드, 볼륨·PR 계산, 세션 완료 이벤트, 완료 화면, 점진적 과부하 조정 결과 저장, 운동 기록 조회
- 제외: 심박 실시간 미러링·심박 기반 휴식 타이머(ADR-0002), 워치 단독 서버 통신(ADR-0002), Health Connect 쓰기(기획서 7장), 유산소·GPS 운동 추적, 운동 동작 영상·자세 분석
- 다른 명세가 맡는 것: 워치 Tile의 Streak·오늘 칼로리 값은 [Growth](./growth.md) REQ-GROWTH-11과 Coaching이 만든다. Workout은 Data Layer 전달 경로만 공유한다. 조정 결정 호출은 [Coaching](./coaching.md) REQ-COACH-07이 한다.

## 2. 기능 요구사항

### 2.1 루틴

| ID | 요구사항 | 인수 조건 | MVP | 상태 |
|---|---|---|---|---|
| REQ-WORKOUT-01 | AI 추천으로 루틴을 만든다 | 회원 목표·신체 정보·최근 세션을 근거로 Spring `infrastructure/ai`가 FastAPI 루틴 생성(`/ai/routine`)을 호출하고, 결과를 `source=AI` 루틴으로 저장한다. 루틴마다 운동 목록과 운동별 목표 세트·횟수·무게·휴식 시간이 있다. AI가 응답하지 않으면 503 `WORKOUT_ROUTINE_UNAVAILABLE` (가정)과 직접 생성 안내 | 2 | 제안 |
| REQ-WORKOUT-02 | 루틴을 직접 만들고 고친다 | 운동 카탈로그에서 운동을 고르고 목표 세트·횟수·무게·휴식을 입력해 `source=MANUAL`로 저장한다. AI 루틴도 같은 방식으로 수정할 수 있다. 목표 세트 0 이하·무게 음수는 400 `INVALID_INPUT` | 2 | 제안 |
| REQ-WORKOUT-03 | 루틴에 운동일을 지정한다 | 루틴마다 `scheduled_date`가 있고 같은 날짜에 활성 루틴은 하나다 (가정). 날짜가 지난 미수행 루틴은 `SKIPPED`로 바뀐다 (가정: 자정 배치, Asia/Seoul) | 2 | 제안 |
| REQ-WORKOUT-04 | 운동 카탈로그를 제공한다 | 운동명·부위·장비가 있는 카탈로그를 이름 검색과 부위 필터로 돌려준다. 초기 데이터는 시드로 넣는다 (가정: 웨이트 운동 50개 내외). 사용자 정의 운동은 미결 | 2 | 제안 |

### 2.2 워치로 루틴 전달

| ID | 요구사항 | 인수 조건 | MVP | 상태 |
|---|---|---|---|---|
| REQ-WORKOUT-05 | 다음 운동일 루틴을 워치에 미리 내려준다 | 폰이 다음 운동일 루틴을 Data Layer `DataClient`(DataItem)로 워치에 전달한다. 시점은 앱 실행 시와 매일 저녁 예약 작업 (가정: 21시, WorkManager). 워치가 범위 밖이어도 DataItem이 보관됐다가 재연결 시 도착한다 | 2 | 제안 |
| REQ-WORKOUT-06 | 루틴에 이전 기록과 추천 무게를 함께 담는다 | 전달하는 루틴의 운동마다 지난 세션의 마지막 세트(무게×횟수)와 오늘 목표 무게가 들어 있어, 워치가 서버 없이 "지난번 80×8 · 오늘 82.5×8"을 보여줄 수 있다 | 2 | 제안 |
| REQ-WORKOUT-07 | 워치는 서버와 인증을 모른다 | 워치 모듈에 서버 주소·토큰·네트워크 클라이언트가 없다. 워치 → 서버 경로는 항상 폰을 거친다. Konsist `wear-no-network` 규칙이 통과한다 | 2 | 제안 |

### 2.3 Workout Mode (워치 · 폰)

| ID | 요구사항 | 인수 조건 | MVP | 상태 |
|---|---|---|---|---|
| REQ-WORKOUT-08 | 워치에서 운동을 시작한다 | 캐시된 오늘 루틴이 있으면 워치 앱 실행 → 시작까지 3탭 이하. 폰 연결이 없어도 시작할 수 있다. 캐시된 루틴이 없으면 자유 운동으로 시작한다 (가정) | 2 | 제안 |
| REQ-WORKOUT-09 | 폰에서도 운동을 시작하고 기록한다 | 폰 앱 실행 → 운동 시작 3탭 이하. 폰 Workout Mode는 워치와 같은 세트 기록·휴식 타이머·이전 기록 표시를 제공한다 | 2 | 제안 |
| REQ-WORKOUT-10 | 세션 주인은 먼저 시작한 기기 하나다 | 한 기기가 세션을 시작하면 시작 이벤트를 `MessageClient`로 다른 기기에 알리고, 다른 기기는 그 세션을 읽기 전용으로 보여준다. 읽기 전용 기기에서는 세트 완료·수정이 막혀 있다. 두 기기에서 거의 동시에 시작하면 시작 시각이 빠른 쪽이 주인이다 (가정) | 2 | 제안 |
| REQ-WORKOUT-11 | 세트 완료는 1탭이다 | 세트 화면의 완료 버튼 1탭으로 현재 목표 무게×횟수가 기록되고, 진동 후 휴식 타이머가 시작되며 다음 세트가 준비된다 | 2 | 제안 |
| REQ-WORKOUT-12 | 무게와 횟수를 2탭 이하로 바꾼다 | 세트 화면에서 무게 또는 횟수를 2탭 이하로 바꿀 수 있다 (가정: 무게 증감 단위 2.5kg, 횟수 1회). 바꾼 값이 그 세트에 기록된다 | 2 | 제안 |
| REQ-WORKOUT-13 | 이전 기록은 세트 화면에 항상 보인다 | 세트 화면에 해당 운동의 지난 세션 기록이 스크롤 없이 보인다. 첫 수행이면 "첫 기록" 류의 문구 (가정) | 2 | 제안 |
| REQ-WORKOUT-14 | 휴식 타이머가 자동으로 돈다 | 세트 완료 후 그 운동의 휴식 시간(루틴 값, 기본 가정 90초)으로 타이머가 시작되고, 끝나면 진동한다. 건너뛰기와 30초 연장 (가정)을 제공한다 | 2 | 제안 |
| REQ-WORKOUT-15 | 루틴에 없는 세트·운동을 추가하고 건너뛴다 | 운동 중에 세트를 추가하거나 운동을 건너뛸 수 있다. 건너뛴 운동은 세트가 0인 채로 세션에 남는다 (가정) | 2 | 제안 |
| REQ-WORKOUT-16 | 심박을 세션 요약으로 남긴다 | 워치가 세션 중 Health Services로 심박을 샘플링하고, 세션에는 평균·최대 심박과 소모 kcal만 저장한다. 권한을 거부하면 심박 없이 기록이 계속된다. 폰 단독 세션은 심박이 비어 있다 | 2 | 제안 |
| REQ-WORKOUT-17 | 운동을 종료한다 | 종료 버튼으로 세션이 끝나고 종료 시각이 기록된다. 세트가 하나도 없는 세션은 저장하지 않는다 (가정). 종료를 누르지 않고 마지막 세트 후 일정 시간이 지나면 자동 종료한다 (가정: 60분) | 2 | 제안 |

### 2.4 세션 전달과 업로드

| ID | 요구사항 | 인수 조건 | MVP | 상태 |
|---|---|---|---|---|
| REQ-WORKOUT-18 | 워치는 세션을 로컬에 먼저 쓴다 | 워치 세션·세트는 완료 즉시 워치 Room에 저장된다. 앱이 종료되거나 재부팅돼도 기록이 남는다 | 2 | 제안 |
| REQ-WORKOUT-19 | 워치 세션을 폰으로 넘긴다 | 세션 종료 후 워치가 `DataClient`로 세션(세트·심박 요약·소모 kcal·client_uuid)을 폰에 전달한다. 폰이 범위 밖이면 보관했다가 재연결 시 전달된다. 폰이 받은 것이 확인되면 워치 로컬 사본을 정리한다 (가정: 7일 보관 후 삭제) | 2 | 제안 |
| REQ-WORKOUT-20 | 폰은 오프라인에서도 세션을 잃지 않는다 | 폰이 받은 세션과 폰에서 기록한 세션은 Room에 `pending_upload`로 먼저 저장되고, WorkManager가 네트워크 복구 시 업로드를 재시도한다. 업로드가 성공하면 상태가 바뀐다. 식사·코칭은 오프라인 저장하지 않는다(REQ-NF-01) | 2 | 제안 |
| REQ-WORKOUT-21 | 업로드는 멱등하다 | 세션에는 시작한 기기가 만든 `client_uuid`가 있다. 같은 UUID가 다시 오면 서버는 새 세션을 만들지 않고 기존 세션을 돌려준다(성공 응답). 이벤트도 다시 발행하지 않는다 | 2 | 제안 |
| REQ-WORKOUT-22 | 서버는 세션을 검증해 저장한다 | 종료 시각이 시작보다 이르거나, 미래 시각이거나, 세트의 무게·횟수가 음수면 400 `INVALID_INPUT`. 다른 회원의 루틴 ID는 404. 오래된 세션 업로드는 허용한다 (가정: 30일 이내) | 2 | 제안 |

## 3. Data Layer 의존 (워치 ↔ 폰)

- 루틴 ↓ 와 세션 ↑ 은 `DataClient`(DataItem), 시작·종료·소유권 알림은 `MessageClient`. 연결 끊김 처리는 DataClient에 맡기고 앱이 별도 재시도 큐를 만들지 않는다(ADR-0002).
- Data Layer 경로와 페이로드 모양은 `:core`에 한 벌로 두고 폰·워치가 같이 쓴다. 바꾸면 B 리뷰가 필수다.
- 같은 Data Layer 경로로 Growth·Coaching의 Tile 값도 내려간다(REQ-GROWTH-11). 경로 이름은 도메인별로 나눈다 (가정: `/workout/routine`, `/workout/session`, `/tile/summary`).
- 실기기 왕복(루틴 ↓, 세션 ↑ 1회 성공)은 2주차 말 스파이크로 먼저 검증한다(기획서 8장).

## 5. 이벤트와 공개 조회

| 구분 | 이름 | 시점·용도 | 페이로드·반환 |
|---|---|---|---|
| 발행 | `WorkoutSessionCompleted` | 세션 업로드 커밋 후(폰이 올린 시점) | memberId, sessionId, totalVolumeKg, burnedKcal, prs[] |
| 공개 조회 | 오늘 세션 존재 여부 (`hasSessionToday`) | Growth 일일 미션 | boolean |
| 공개 조회 | 하루 소모 kcal (가정: `WorkoutQueryService.getDailyBurned`) | Coaching 칼로리 밸런스 보조 | kcal 합계 DTO |
| 받는 것 (미결) | 루틴 조정 결정 | Coaching이 FastAPI에서 받은 결정을 Workout에 반영 | memberId, exerciseId, decision, nextWeightKg, fromSessionId |

구독하는 이벤트는 지금 없다. 조정 결정을 이벤트로 받기로 하면 이벤트 목록에 새 이벤트를 추가하고 이 표를 고친다. 상세는 [이벤트 목록](../renewal/events.md).
