# ADR-0002: 워치는 오프라인 우선 보조 앱(Companion) — 서버·인증을 모른다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-10-03 |
| 결정자 | 리뉴얼 기획 단계 팀 결정 (E 주도) |
| 관련 | [기획서](../renewal/plan.md) |

## 맥락

웨이트 세트 기록은 워치가 핵심 UX다. 설계 기준 시나리오는 **"폰은 사물함, 워치만 차고 운동"** —
헬스장 사물함과 운동 구역은 블루투스 범위(~10m)를 벗어나는 경우가 흔하다.
따라서 워치는 폰 연결 없이도 한 세션을 끝까지 기록할 수 있어야 한다.

## 결정

워치는 **Companion 앱**이다.
- 서버와 직접 통신하지 않고, 인증 토큰을 갖지 않는다.
- 폰이 `DataClient`(DataItem)로 **오늘 루틴을 미리 내려준다.** 연결이 끊겨도 보관됐다가 재연결 시 전달된다.
- 워치는 세션(세트·휴식·심박 요약)을 **로컬 Room에 먼저 쓰고**, 폰 연결 시 `DataClient`로 올린다. 서버 업로드는 폰이 한다.
- 시작/종료 같은 즉시 이벤트는 `MessageClient`.
- **워치에서도 운동을 시작할 수 있다**(루틴 사전 캐시 전제).
- **세션 소유권 단일**: 먼저 시작한 기기가 세션 주인, 다른 기기는 읽기 전용 미러. 양쪽에서 동시에 세트를 쓰는 충돌을 구조적으로 없앤다.
- 심박은 Health Services로 샘플링하되 **세션 요약(평균·최대, 소모 kcal)만** 전송한다. 실시간 미러링 없음.
- 워치 부가 기능은 **Streak/오늘 칼로리 Tile**(읽기 전용)까지. 식사 기록은 워치에 없다.

## 근거

- **인증·토큰 갱신·네트워크 재시도를 워치에 복제하지 않는다.** 워치 로그인 UX도 사라진다.
- **DataClient는 오프라인을 기본으로 설계된 API다.** 연결 끊김을 앱이 처리하지 않아도 된다.
- 세션 소유권을 단일화하면 **CRDT·머지 로직이 필요 없다.** 8주 프로젝트에서 가장 위험한 "양방향 동기화 충돌"을 제거한다.
- 실시간 심박 미러링은 사물함 시나리오(폰 부재)와 모순된다.

## 고려한 대안

- **독립 앱(Standalone, 서버 직접 호출)**: 폰 없이 완전 동작하지만 인증·네트워크·보안을 워치에 복제. Wi-Fi/LTE 의존. 기각.
- **혼합(기본 Companion, 폰 부재 시 직접 업로드)**: 두 경로 모두 구현·테스트. 8주에 과함. 기각.
- **폰에서만 시작, 워치는 이어받기**: 시작 시점에 폰 연결을 보장해야 해서 사물함 시나리오를 깨뜨림. 기각.
- **심박 기반 휴식 타이머**: 차별 포인트지만 튜닝 필요. 범위 밖(후속 후보).

## 결과

- 폰 앱이 "다음 운동일 루틴을 미리 내려주는" 책임을 가진다(스케줄 또는 앱 실행 시).
- 서버 입장에서 세션은 항상 폰이 업로드한다. 워치 전용 API 없음.
- Data Layer 왕복(루틴 ↓, 세션 ↑)을 **2주차 말 실기기 스파이크**로 검증한다(기반 체크리스트 항목).
- Workout 수직 소유자(B)가 폰·워치 양쪽 Data Layer 코드를 모두 소유한다. 동기화 버그가 두 사람 사이에 떨어지지 않는다.
