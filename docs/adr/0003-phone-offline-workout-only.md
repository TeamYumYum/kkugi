# ADR-0003: 폰 오프라인 범위는 운동 기록만

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-10-03 |
| 결정자 | 리뉴얼 기획 단계 팀 결정 (E 주도) |
| 관련 | [기획서](../renewal/plan.md) |

## 맥락

UX 수용 기준에 "네트워크 없어도 기록 가능"이 있다. 워치는 ADR-02로 오프라인 우선이 확정됐고,
폰이 어디까지 오프라인을 지원해야 하는지 정해야 한다. 세 상황이 있다:
1. 지하 헬스장·비행기 모드에서 폰으로 세트를 기록할 때
2. 워치에서 끝낸 세션이 폰으로 넘어왔는데 폰도 인터넷이 없을 때
3. 식사 사진을 찍었는데 인터넷이 없을 때

## 결정

폰 오프라인은 **운동 세션만** 지원한다(상황 1·2).
- 세션은 Room에 먼저 쓰고(`pending_upload` 상태), **WorkManager**가 네트워크 복구 시 업로드를 재시도한다.
- 식사·홈·코칭·Growth는 **온라인 전용**. 마지막 응답만 캐시해 보여주고, 쓰기는 네트워크 오류로 안내한다.
- 전체 도메인 로컬 미러 + 양방향 동기화는 하지 않는다.

## 근거

- **식사 기록의 본질은 사진 → 서버 인식이다.** 오프라인 저장은 "인식 결과가 나중에 도착했다"는 별도 알림 UX를 요구하며, 수정 UX(J1)와 엉킨다.
- 코칭·Growth는 서버 계산(이벤트 기반 XP·Streak). 로컬 선반영 후 보정은 **충돌 해결 규칙**을 요구한다.
- 양방향 동기화는 8주 프로젝트에서 가장 자주 터지는 지점이다. 수용 기준은 운동만 오프라인이어도 충족된다.

## 고려한 대안

- **운동 + 식사 사진 보관(상황 3 포함)**: 사진을 로컬에 두고 연결 시 인식 요청. "인식 완료" 알림 UX 추가. 후속 후보.
- **전체 로컬 DB + 양방향 동기화**: 모든 도메인 Room 미러. 충돌 규칙 필요. 기각.
- **오프라인 없음**: 수용 기준 위반. 워치 세션이 폰에 도착했는데 업로드 못 하는 상황이 생김. 기각.

## 결과

- `:core`의 Room은 Workout 테이블(세션·세트·업로드 상태)만 가진다. 다른 feature 모듈은 Room을 쓰지 않는다(규칙 파일).
- 업로드 재시도는 멱등해야 한다 → 세션에 **클라이언트 생성 UUID**를 두고 서버가 중복을 무시한다.
- 홈 화면의 "오늘 칼로리"는 오프라인에서 **마지막 동기화 시각**을 함께 표시한다.
